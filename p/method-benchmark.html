Preliminary public-data benchmark

We found real interoperability edge cases before asking a lab for private data.

WeedDAO reviewed public cannabis lab-result data and a state regulatory CSV template to test whether result meaning can be lost when data moves between representations.

1. <LOQ is a state, not a number Public parsed lab-result data includes values such as <LOQ for cannabinoids. A downstream numeric-only field must either discard that state, coerce it, or preserve it separately.
2. Unit field names vary in downstream representations Observed parsed result objects use both unit and units. That does not mean the source lab is wrong; it means integration code should normalize field identity while preserving source provenance.
3. Limits can become type-unstable Public parsed examples include numeric and string-like values in fields labeled as LOD/LOQ. A robust interoperability layer should separate raw reported text, interpreted numeric limits, and review/confidence.
4. Parsed COAs can contain non-result text in result-shaped objects Public parsed data includes apparent footer/disclaimer/page fragments represented in result-like structures. A normalization layer should not assume every parsed object is a true analyte result.
5. Washington's CCRS lab CSV uses a generic TestValue shape The public template includes TestName, TestValue, and LabTestStatus, but no dedicated unit, LOD, or LOQ columns. Some meaning therefore depends on conventions or external regulatory context.
What WeedDAO does with this:
Preserve raw values, normalize analyte and unit identity, separate result-state semantics from numeric measurements, retain limits and provenance, and flag ambiguous mappings for review.

Important limitation: the lab examples referenced here come from public parsed/curated data, not necessarily production-native exports from the named laboratories. This benchmark describes representation differences; it does not rank or grade laboratories, LIMS vendors, or regulators.
